1. Executive Summary
SIH26263 asks for an APAAR ID-based student data management and verification platform for AICTE-approved institutions. Institutions need to submit and update student-level records; the platform should validate those records, monitor enrolment, detect duplicates and inconsistencies, support authorized verification, integrate with existing systems, protect data and produce reports.
The prototype will be a role-aware web platform. Institution staff import CSV/XLSX student records, preview and validate them, correct issues and submit a versioned batch. AICTE reviewers see institution-level monitoring, intake-versus-enrolment exceptions and potential cross-institution duplicate cases. A clearly labelled mock APAAR adapter keeps the demo functional if authorized live API access is unavailable.
Main differentiator: an explainable student data-quality and reconciliation workflow. Every alert should identify the record/row/field, rule, reason, severity and next action; corrections can be made and checks rerun.
Definition of success
A repeatable demo runs from login → import → validate → findings → correction/revalidation → submit/review → dashboard → report export.
All default demo records are synthetic. Mock verification is visibly marked as simulated.
Every finding is explainable and traceable to a record/row/field.
Server-side roles, institution isolation, privacy controls and audit history work.
The prototype remains useful without live APAAR or AICTE API access.

5. Functional Requirements
FR-01 Authentication and authorization
Login/logout and seeded demo accounts for Institution Admin, Institution Operator and AICTE Admin.
Use salted password hashes if password auth is implemented; never store plaintext secrets.
Every API request is checked for role and institution scope.
FR-02 Institution, programme and intake
Represent institution, programme/course, academic year and approved intake.
Store intake by institution + programme + year; model regular and supernumerary categories separately.
Use seeded illustrative values unless official values are supplied.
FR-03 Bulk import
CSV and XLSX are primary prototype inputs; PDF/OCR is not the main route for tabular student records.
Provide template, upload, column mapping, preview, row count and confirmation.
Handle blank rows, missing columns, duplicate headers, bad types and malformed files gracefully.
Keep import batch ID, uploader, timestamp, original filename and row-level outcomes. Never silently drop invalid rows.
FR-04 Student data fields
At minimum: APAAR ID, institution student ID, institution, academic year, programme/course, admission/enrolment status, seat type, NRI category, OCI status, FN status and timestamps where needed.
Approved intake and actual enrolment are institution/course/year facts, not repeated totals in every student row.
Only include name/DOB/gender or other identity fields if justified by the official data contract and matching purpose.
Do not add Aadhaar number without explicit official requirement and authorized basis. Use internal record IDs as primary keys.
FR-05 Validation engine
Validate required fields, types, allowed values, dates, statuses and references.
Check APAAR ID presence and syntax using confirmed rules; if unconfirmed, mark as configurable syntactic validation.
Check duplicates within batch/institution and across institutions.
Compare enrolled counts with configured intake; handle supernumerary seats through explicit configurable policy.
Every finding has rule code, severity, reason, record/row/field, actual/expected value if known and next action.
FR-06 Duplicate matching
Exact valid APAAR ID match is strongest key.
If ID is missing/invalid, optionally suggest candidate matches using limited fields; name similarity alone must never merge records.
Explain matching signals and threshold; allow reviewer to confirm, dismiss or request more evidence.
Keep records separate until authorized resolution; mask other-institution details from unauthorized users.
FR-07 APAAR verification adapter
Create a provider interface so an authorized service can be integrated later.
Mock adapter outcomes must be clearly named MOCK_VERIFIED, MOCK_NOT_VERIFIED, MOCK_UNAVAILABLE or NEEDS_REVIEW.
Format validation is not official verification. External service outage must not crash core validation.
Do not invent endpoints, credentials, provider responses or official API availability.
FR-08 Submission lifecycle
Prototype states: Draft → Validated → Submitted → Under Review → Accepted / Needs Correction / Rejected. Label these as prototype workflow states, not official AICTE states.
Create new batch/version on resubmission; preserve previous history.
Block submission when configured blocking errors remain; warnings may be allowed per config.
Show counts of total, valid, warnings, errors, duplicates and intake exceptions.
FR-09 Dashboards
Institution view: record counts, valid/invalid rows, missing APAAR IDs, duplicate flags, intake usage, batch status and recent activity.
AICTE view: institution submission progress, enrolment by course/year, exception counts, possible cross-institution duplicates and recent activity.
Metrics update from backend data after actions; filters for year, programme, institution, batch, status and severity.
Use seeded scenarios to demonstrate both healthy and problematic cases.
FR-10 Review and correction
Provide exception queue and candidate-duplicate review.
Authorized reviewer can confirm, dismiss, mark corrected or request information.
Require reason for dismissing a cross-institution duplicate/high-impact issue.
Track actor, timestamp, previous/new state and reason. Never auto-reject or accuse based only on algorithmic match.
FR-11 Verification and certificate display
Provide a limited-purpose record lookup with minimum necessary fields and audit event.
Generate a platform verification reference/receipt, clearly not a government-signed credential.
P1 certificate preview displays institution student ID and APAAR ID with synthetic data and appropriate permissions.
FR-12 Reports
Export filtered error/quality reports to CSV; print-friendly aggregate report if time allows.
Include generation time, institution/year/course filters, record totals and issue counts.
Aggregate analytics must be separated from personally identifiable exports; permissions apply.
FR-13 Audit and consent/authority
Audit imports, validation, submission, corrections, reviews, exports and verification lookups.
Record actor, action, object, timestamp, outcome and reason; normal users cannot edit audit events.
Capture consent/authority metadata where required; do not imply a checkbox alone establishes legal consent.
Mask identifiers in logs and avoid storing raw student payloads in logs.
FR-14 APIs and interoperability
Versioned REST API under /api/v1; consistent JSON schemas and errors.
Expose imports, batches, validation, records, dashboards, reviews, verification and reports.
OpenAPI/Swagger and docs/API.md with examples; health endpoint; external integrations behind adapters.

How to implement a defensible quality score
If time permits, score completeness, validity, consistency and duplication with transparent weighted rules. Show component counts and formula. Call it a dataset quality score, not a ranking of institutions. A high aggregate must not hide severe individual errors.
AI/ML guidance
Do not add an LLM just to claim AI. Exact identifiers and deterministic rules are more reliable for many checks. Mandatory Development → Testing → Audit → Improvement → Verification Cycle
Plan and define acceptance criteria: 
state the objective, requirements, files/modules, risks, test plan and explicit exit gate.
Develop the smallest vertical slice: 
implement only the current scope and preserve working behavior.
Test: 
run unit, API, integration and relevant UI/end-to-end tests; include positive, negative and boundary cases.
Generate an initial audit report: 
list files changed, requirements covered, tests run/results, failures, gaps, security/privacy risks and limitations.
Analyze and prioritize improvements: 
find root causes and rank defects by severity and impact; do not broaden scope.
Implement improvements: 
fix confirmed defects and add regression tests.
Verify again: 
rerun failed tests, regression tests and the full relevant suite; check previous features remain working.
Generate a final verification audit: 
map each acceptance criterion to evidence and mark PASS, FAIL, BLOCKED or NOT TESTED; list residual risks.
Gate the next phase: 
proceed only when all critical criteria/tests pass. Otherwise repeat improvement, testing and verification, or report a genuine blocker.
A phase is complete only after implementation, testing, audit, improvement, retesting and final verification are evidenced.

17. Security, Privacy and Responsible Use
Treat student identifiers and academic records as sensitive; use synthetic records by default.
Collect only fields justified by the official data contract. Do not add Aadhaar number just because it is associated with the broader APAAR ecosystem.
Mask identifiers in lists/logs and restrict full values to authorized use.
Enforce server-side RBAC and institution scope on every route/query.
Use HTTPS in deployed environments; secrets in environment variables, never Git.
Validate upload types/sizes and handle malformed files safely; use parameterized queries/ORM.
Do not log raw student records; audit sensitive lookups and exports.
Restrict cross-institution matching details to authorized reviewers.
Consent/authority UI must reflect the actual workflow; a checkbox alone is not a guarantee of legal compliance.
Never auto-reject a student or auto-merge records based solely on a matching score.
This is an engineering brief, not legal advice. Production deployment requires confirmation of applicable Indian data-protection obligations, official APAAR terms, authorized data sharing, retention and access policies.
